# Static dashboard architecture review

## Verdict

**PASS.** No concrete security or functional blocker was found in the proposed separate Nginx image, separate Deployment, and direct dashboard-to-API architecture. Implementation can begin. This review applies to the architecture against API commit `4b41f50`; it is not an implementation or browser-QA approval.

## Reviewed boundaries

- The API owns management, inference and streaming. Nginx serves only static assets and public runtime configuration. No embedded assets or dashboard API proxy are needed.
- HTTPS sibling origins under the same registrable domain can use the current host-only, HttpOnly, `SameSite=Strict` management cookie. Dashboard fetches must explicitly use `credentials: "include"`, including login, so the browser accepts the API's cookie and sends it on later requests. Cross-origin and cross-site are different relationships; unrelated public sites are outside this deployment contract. See [Fetch credentials](https://developer.mozilla.org/en-US/docs/Web/API/Request/credentials) and [same-site origin relationships](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site).
- Exact credentialed CORS belongs only to the management subtree, with fixed methods/headers and the existing custom mutation header retained. The browser's CORS check and the mutation-header requirement work together; CORS is not a replacement for session authentication or resource ownership. The maintained [tower-http CORS layer](https://docs.rs/tower-http/latest/tower_http/cors/struct.CorsLayer.html) supplies the mechanism.
- Provider metadata and UI labels are untrusted content and must enter text nodes or DOM properties. Passwords, OAuth codes and one-time inference tokens are transient. The account/session generation guard described in the architecture prevents late asynchronous results from restoring stale account data after logout or an account change.
- Separate image repositories, digest artifacts and manifest publication preserve independent API/dashboard deployment. The [unprivileged Nginx image](https://github.com/nginx/docker-nginx-unprivileged) fits the static-only server and writable temporary-directory requirements.

## Implementation constraints and acceptance checks

1. **CORS ordering and scope.** Wrap the complete management subtree outside its session and mutation middleware. Preflight must succeed without a session, and allowed-origin errors such as 400/401 must remain readable by the dashboard. Do not attach the layer after merging inference routes. Test allowed and hostile origins, credential/method/header behavior, unauthenticated preflight, error responses, and the absence of inference CORS. A hostile request's HTTP status alone does not prove browser authorization; inspect the CORS response headers.
2. **Stable API selectors.** The existing API Deployment selector is immutable and its Service currently selects only `app.kubernetes.io/name=llmproxy` plus the release instance. Give dashboard Pods a genuinely disjoint matching label/name; an extra dashboard component label does not stop the existing API Service from selecting them if the original two labels still match. Preserve the API Deployment's existing selector when extending the chart, and test both Service selectors against both Pod label sets.
3. **Origin/config correctness.** Accept complete HTTP(S) origins without user-info, path, query or fragment; reject wildcard/opaque origins. The Helm value used for API CORS must be the dashboard's public origin, while frontend `apiUrl` must be the API's public origin. Serialize runtime config with a JSON encoder. Treat both as explicit deployment settings rather than baking in the illustrative domains. Document the same-site HTTPS deployment requirement and local HTTP cookie setting.
4. **Browser lifecycle.** Stop OAuth polling on terminal state, dialog close, logout and account transition. Check the current account/session generation before applying every asynchronous result, including rejected requests. Keep route edits local until one successful PUT; retain submitted values on recoverable errors. Clear passwords and one-time tokens when their flow ends.
5. **Static/container behavior.** Missing assets should return a real 404 rather than the application HTML. Revalidate the entry HTML and runtime config so configuration changes become visible. Check Nginx startup under the configured non-root identity, read-only config/static mounts, and writable `/tmp`. No proxy location may forward API traffic.

These points refine the approved design rather than add new subsystems. Final approval requires the planned Rust/CORS, browser, container, Helm and workflow checks. Real subscription login, image publication and cluster rollout remain outside the authorized validation scope.
