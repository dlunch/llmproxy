# Routing and streaming p50 follow-up

- Date: 2026-10-22
- Baseline: `8ed9f5f`
- Status: implemented and locally verified

## Change and validation

Provider-state loading now reads usage totals and quota windows in one LEFT JOIN. Ordered rows are grouped without the intermediate provider-ID list or repeated provider searches. Account/configured-provider filtering and providers with no quota windows are preserved. Routing uses three read statements instead of four; usage counters, atomic finalization and current quota rules are unchanged.

Each gateway request now pins one absolute-deadline timer and one cancellation future, reused during provider setup, event reads and downstream sends. This removes repeated timer/cancellation registration per chunk while retaining cancellation priority, deadlines, backpressure and durable terminal accounting.

The existing gateway integration fixture now checks multiple/no-quota providers explicitly and verifies timeout after the stream has reported usage, including persisted terminal state and totals. The full suite passed 24 distinct tests, including official Claude CLI 2.1.307 against a fake local API. Formatting, locked Clippy with warnings denied and whitespace checks passed. No dependency, schema or public interface changed.

## Measurement

The unchanged release API benchmark ran in baseline, changed, changed, baseline order, with no concurrent builds or tests. Both versions use the same full JSON logger and buffered worker. Release executables were copied separately before measuring, and package release artifacts were cleaned before the changed build. All four runs passed.

Each of 24 combinations uses five warm-up batches and 50 measured batches, with concurrency one or four, both APIs and response modes, short/128 KiB payloads and zero/100,000 seeded history rows. Large output contains 2,048 synthetic 64-byte deltas. The local PostgreSQL database, routing, accounting and logging are included; seed creation and the final log drain are outside per-request timings. Live provider latency, CLI startup, client network transport and the deployed logging sink are excluded.

Values below are the arithmetic mean of each statistic from two runs, not pooled percentiles. First text excludes metadata-only frames. Collected responses expose text with their complete body. Raw per-run statistics, including first-frame timing and throughput, are in [20261022-p50-latency-samples.csv](20261022-p50-latency-samples.csv).

Total p50 was lower in 19 of 24 measured combinations. For short collected responses at concurrency four, Chat changed from 23.35 to 20.46 ms (12.4% lower) and Responses from 23.19 to 19.81 ms (14.6% lower). Five combinations instead showed 2.4–19.2% higher p50; large-stream first-text and p95 results were also mixed. These are observed local results, not evidence of a uniform speedup or of the individual cause of each difference.

## Limits

The host was shared and PostgreSQL background work remained enabled. Tail latency varied substantially in some large-output runs; two runs do not establish statistical significance or production capacity. These measurements combine both code changes and do not isolate their individual contribution. Hardware CPU profiling was unavailable under host permissions; no CPU-profile claim is made.

The earlier tradeoffs remain: counter updates serialize completions for the same account, and a full non-lossy log queue applies backpressure. The changes do not establish that every workload is faster than the pre-counter implementation. Live subscription and multi-replica load were not measured.
